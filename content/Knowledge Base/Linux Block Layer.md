## 1. 개요

Linux Block Layer는 파일시스템이나 애플리케이션이 만든 블록 I/O 요청을 장치 드라이버로 전달하고 큐·병합·스케줄링·완료 처리를 중재하는 커널 계층이다.

이 계층은 파일 이름을 이해하지 않는다. 어떤 블록 장치의 어느 논리 주소를 읽거나 쓸 것인지와 요청의 크기·방향·완료 상태를 다룬다. 현대 Linux의 `blk-mq`는 SSD·NVMe 같은 병렬 장치의 처리 능력을 활용할 수 있도록 여러 소프트웨어·하드웨어 큐를 사용한다.[^blkmq]

## 2. 블록 요청의 의미

운영체제가 보는 블록 장치는 번호가 붙은 논리 주소 공간이다.

```text
/dev/sdb

LBA 0 | LBA 1 | LBA 2 | LBA 3 | ...
```

파일시스템이 `report.txt`의 내용을 저장할 블록을 결정하면 블록 계층에는 다음과 같은 의미의 요청이 전달된다.

```text
장치: /dev/sdb
작업: WRITE
위치: LBA 5000부터
크기: 16 KiB
```

HDD는 헤드와 플래터를 이용하고 SSD는 컨트롤러가 NAND 위치를 관리하지만, Linux의 상위 계층은 장치가 제공하는 논리 블록 인터페이스를 사용한다. 논리 주소와 실제 매체 위치의 대응은 장치 컨트롤러나 스토리지 시스템이 처리할 수 있다.

## 3. 파일 쓰기와 장치 전달

```mermaid
flowchart LR
    A["애플리케이션"] --> B["VFS"]
    B --> C["파일시스템"]
    C --> D["블록 I/O 요청"]
    D --> E["Linux Block Layer"]
    E --> F["SCSI·NVMe·가상 장치 드라이버"]
    F --> G["저장장치"]
```

파일시스템은 파일 이름·디렉터리·권한·빈 공간·블록 매핑을 관리한다. 블록 계층은 그 결과로 만들어진 I/O를 장치에 전달한다. 따라서 “어느 파일인가”는 파일시스템의 질문이고 “어느 장치 주소를 읽고 쓰는가”는 블록 계층의 질문이다.

요청이 완료되면 장치 드라이버가 완료 상태를 블록 계층에 알리고, 그 결과가 파일시스템과 요청한 프로세스로 돌아간다. 완료 순서에 필요한 일관성은 상위 파일시스템과 애플리케이션의 규칙까지 함께 고려해야 한다.[^blkmq]

## 4. 큐와 병렬 처리

`blk-mq`는 CPU에 가까운 소프트웨어 큐와 장치 제출 경로에 가까운 하드웨어 디스패치 큐를 사용한다.[^blkmq]

```text
프로세스·CPU
   ↓
소프트웨어 큐
   ├── 인접 요청 병합 가능
   ├── I/O 스케줄러 적용 가능
   └── 대기와 공정성 관리
   ↓
하드웨어 디스패치 큐
   ↓
장치 드라이버와 저장장치
```

기계식 HDD에서는 헤드 이동을 줄이는 요청 순서가 중요했고, SSD·NVMe에서는 여러 요청을 동시에 처리하는 병렬성이 중요해졌다. 블록 계층은 장치 특성과 드라이버가 제공하는 큐에 맞춰 요청을 전달한다.

## 5. 로컬·원격 블록 장치

블록 계층 아래에는 여러 종류의 장치 경로가 올 수 있다.

```text
로컬 SATA SSD     → SCSI 계열 드라이버 → 장치
로컬 NVMe SSD     → NVMe 드라이버 → 장치
iSCSI LUN         → SCSI → iSCSI Initiator → TCP/IP → Target
가상 머신 디스크 → 가상 블록 드라이버 → 하이퍼바이저·스토리지
```

물리적으로 원격에 있는 [[SAN]]의 LUN도 호스트에 블록 장치로 연결되면 파일시스템과 블록 계층 위에서는 디스크와 비슷한 방식으로 다룰 수 있다. 실제 장애 범위에는 네트워크·스위치·Target·스토리지 컨트롤러가 추가된다.

## 6. VFS와의 차이

| 계층 | 중심 역할 | 주로 다루는 대상 |
|---|---|---|
| [[VFS]] | 여러 파일시스템의 공통 파일 인터페이스 | 경로·파일·inode·마운트 |
| 파일시스템 | 파일과 블록 주소의 연결 | 디렉터리·메타데이터·공간 할당 |
| Linux Block Layer | 블록 I/O 전달과 큐 관리 | 장치·LBA·읽기·쓰기 요청 |

파일 스토리지의 NFS 요청은 클라이언트의 로컬 블록 장치를 직접 다루지 않고 네트워크 파일 프로토콜로 이어진다. 오브젝트 스토리지의 S3 요청도 HTTP API 계층으로 전달된다. 세 접근 방식이 모두 최종적으로 디스크를 사용할 수 있지만, 클라이언트에서 같은 경로를 거치는 것은 아니다.
