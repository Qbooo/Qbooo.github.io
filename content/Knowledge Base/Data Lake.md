## 1. 개요

Data Lake(데이터 레이크)는 정형·반정형·비정형 데이터를 다양한 분석 목적에 활용할 수 있도록 저장하는 데이터 아키텍처이다.

원본에 가까운 데이터를 보관하고 필요한 처리와 분석을 이후에 적용할 수 있다.[^2]

## 2. 다양한 원본 데이터를 보관하는 이유

분석에 쓸 열과 형식을 처음부터 모두 정하기 어려운 데이터가 있다. 서비스 로그, 이미지, 센서 데이터처럼 형태가 다른 원본을 보관해 두면 나중에 새로운 분석이나 AI 학습에 활용할 수 있다. 데이터 레이크는 이렇게 다양한 데이터를 모으되, 찾고 해석할 수 있는 메타데이터와 관리 기능을 함께 갖추는 접근이다.[^2]

예를 들어 웹 서비스의 JSON 로그를 원본 영역에 보관하고, 일별 분석에는 필요한 항목을 Parquet 파일로 정제해 사용할 수 있다. 원본과 분석용 데이터는 같은 정보를 서로 다른 목적으로 담는다. 원본을 남겼다고 분석 테이블이 자동으로 준비되는 것은 아니며 수집·변환·카탈로그와 분석 엔진이 각각 역할을 맡는다.

파일의 배치도 읽는 방식에 영향을 준다. 날짜별 파티션을 사용하면 특정 날짜의 분석에서 관련 영역만 읽을 수 있고, 열 지향 파일 형식은 필요한 열을 읽는 분석에 유리할 수 있다. 데이터 레이크의 가치는 저장 용량뿐 아니라 다양한 원본을 다시 해석하고 활용할 수 있는 구조에 있다.[^d-partition][^d-columnar]

## 3. 저장소와 분석 계층

오브젝트 스토리지는 대규모 데이터 레이크의 저장 기반으로 자주 사용되지만, 버킷 하나를 만드는 것만으로 데이터 레이크가 완성되지는 않는다. 원본뿐 아니라 정제된 데이터도 보관할 수 있다. 데이터를 찾는 데 필요한 카탈로그와 품질·권한 관리가 갖춰지지 않으면, 데이터가 쌓여도 활용하기 어렵다.[^2]

| 계층 | 역할 |
|---|---|
| 수집 | 로그, 파일, 업무 데이터 유입 |
| 저장 | 원본과 가공 데이터 보관 |
| 카탈로그·거버넌스 | 데이터 위치·의미·권한·품질 관리 |
| 처리·분석 | 변환, SQL 분석, AI 학습 등에 활용 |

이 표는 이해를 위한 논리적 구분이며 특정 제품의 필수 구성도는 아니다.

## 4. 데이터 저장·처리·분석 구조

데이터 레이크의 처리 흐름은 업무 DB·로그·파일 같은 원천 → 수집 파이프라인 → 원본 영역 → 정제·가공 영역 → 카탈로그와 분석 엔진 → 분석·AI 애플리케이션으로 설명할 수 있다. 저장소에는 데이터 파일이 놓이고, 수집·변환 엔진은 서버·컨테이너·관리형 연산 자원에서 실행된다. 카탈로그는 파일 위치·테이블 스키마·파티션 등의 메타데이터를 제공하고 쿼리 엔진은 이 정보를 사용해 실제 파일을 읽는다. 모든 요소가 같은 버킷이나 같은 서버 안에 있어야 하는 것은 아니다.[^2]

예를 들어 원본 JSON 로그를 날짜별로 수집해 Parquet 파일로 정제했다고 하자. JSON의 필드 이름이 있다는 사실과 분석 테이블의 데이터 유형·열 정의·파티션이 등록되어 있다는 사실은 다르다. Schema-on-read는 읽을 때 구조를 해석하는 관점이지 스키마·품질 관리가 불필요하다는 뜻이 아니다. 레이크하우스의 테이블 형식·트랜잭션 메타데이터는 파일 위에 테이블 상태와 변경 규약을 더하는 계층으로 이해할 수 있다.

파일이 존재해도 카탈로그의 경로·파티션이 누락되면 기대한 쿼리 결과가 나오지 않을 수 있다. 반대로 테이블이 보여도 분석 엔진에 실제 객체 접근 권한이 없으면 읽을 수 없다. 데이터 위치, 메타데이터와 실행 신원은 서로 연결되어야 한다.

## 5. AI 데이터와 스토리지

AI 학습은 레이크의 데이터를 정제해 데이터셋으로 만들고, 학습 결과를 평가하는 흐름으로 이어질 수 있다. 같은 분석을 다시 수행하려면 원본·가공 데이터의 버전과 변환 이력을 구별해야 한다. 데이터 계보(lineage)는 원천과 변환 관계를 추적하는 정보이며, 그 자체가 데이터 보존·접근 권한을 대신하지는 않는다.[^v-lineage]

[[NGOS]] 같은 [[Object Storage]]는 저장 기반으로 검토할 수 있지만, 카탈로그·분석 엔진·접근 정책까지 자동으로 대신하는 것은 아니다. 레이크의 모든 데이터를 고속 GPU 스토리지에 보관할 필요는 없으며, 실제 접근 패턴에 맞춰 계층을 나눌 수 있다.

## 6. 웨어하우스와의 관계

[[Data Warehouse]]는 일관된 지표와 SQL 분석을 위해 데이터를 정제·구조화하는 데 중점을 둔다. 데이터 레이크는 더 다양한 형식과 미래 분석 가능성을 수용하는 데 유리하다. 다만 현대 플랫폼에서는 두 방식의 기능이 겹치고 레이크하우스처럼 결합하기도 한다.[^1]
