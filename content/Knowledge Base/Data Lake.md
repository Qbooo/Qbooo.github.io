## 1. 개요

Data Lake(데이터 레이크)는 정형·반정형·비정형 데이터를 다양한 분석 목적에 활용할 수 있도록 저장하는 데이터 아키텍처이다.

원본에 가까운 데이터를 보관하고 필요한 처리와 분석을 이후에 적용할 수 있다.[^2]

## 2. 저장소와 분석 계층

오브젝트 스토리지는 대규모 데이터 레이크의 저장 기반으로 자주 사용되지만, 버킷 하나를 만드는 것만으로 데이터 레이크가 완성되지는 않는다. 원본뿐 아니라 정제된 데이터도 보관할 수 있고, 찾을 수 있는 카탈로그와 신뢰할 수 있는 품질·권한 관리가 없으면 활용하기 어려운 데이터가 쌓일 수 있다.[^2]

| 계층 | 역할 |
|---|---|
| 수집 | 로그, 파일, 업무 데이터 유입 |
| 저장 | 원본과 가공 데이터 보관 |
| 카탈로그·거버넌스 | 데이터 위치·의미·권한·품질 관리 |
| 처리·분석 | 변환, SQL 분석, AI 학습 등에 활용 |

이 표는 이해를 위한 논리적 구분이며 특정 제품의 필수 구성도는 아니다.

## 3. 웨어하우스와의 관계

[[Data Warehouse]]는 일관된 지표와 SQL 분석을 위해 데이터를 정제·구조화하는 데 중점을 둔다. 데이터 레이크는 더 다양한 형식과 미래 분석 가능성을 수용하는 데 유리하다. 다만 현대 플랫폼에서는 두 방식의 기능이 겹치고 레이크하우스처럼 결합하기도 한다.[^1]

## 4. AI 데이터와 스토리지

AI 학습은 레이크의 데이터를 정제해 데이터셋으로 만들고, 학습 결과를 평가하는 흐름으로 이어질 수 있다. 같은 분석을 다시 수행하려면 원본·가공 데이터의 버전과 변환 이력을 구별해야 한다. 데이터 계보(lineage)는 원천과 변환 관계를 추적하는 정보이며, 그 자체가 데이터 보존·접근 권한을 대신하지는 않는다.[^v-lineage]

[[NGOS]] 같은 [[Object Storage]]는 저장 기반으로 검토할 수 있지만, 카탈로그·분석 엔진·접근 정책까지 자동으로 대신하는 것은 아니다. 레이크의 모든 데이터를 고속 GPU 스토리지에 보관할 필요는 없으며, 실제 접근 패턴에 맞춰 계층을 나눌 수 있다.

## 5. 저장 파일이 분석 결과가 되는 구성

데이터 레이크의 예시 흐름은 업무 DB·로그·파일 같은 원천 → 수집 파이프라인 → 원본 영역 → 정제·가공 영역 → 카탈로그와 분석 엔진 → 분석·AI 소비자다. 저장소에는 데이터 파일이 놓이고, 수집·변환 엔진은 서버·컨테이너·관리형 연산 자원에서 실행된다. 카탈로그는 파일 위치·테이블 스키마·파티션 등의 메타데이터를 제공하고 쿼리 엔진은 이 정보를 사용해 실제 파일을 읽는다. 모든 요소가 같은 버킷이나 같은 서버 안에 있어야 하는 것은 아니다.[^2]

예를 들어 원본 JSON 로그를 날짜별로 수집해 Parquet 파일로 정제했다고 하자. JSON의 필드 이름이 있다는 사실과 분석 테이블의 데이터 유형·열 정의·파티션이 등록되어 있다는 사실은 다르다. Schema-on-read는 읽을 때 구조를 해석하는 관점이지 스키마·품질 관리가 불필요하다는 뜻이 아니다. 레이크하우스의 테이블 형식·트랜잭션 메타데이터는 파일 위에 테이블 상태와 변경 규약을 더하는 계층으로 이해할 수 있다.

파일이 존재해도 카탈로그의 경로·파티션이 누락되면 기대한 쿼리 결과가 나오지 않을 수 있다. 반대로 테이블이 보여도 분석 엔진에 실제 객체 접근 권한이 없으면 읽을 수 없다. 데이터 위치, 메타데이터와 실행 신원은 서로 연결되어야 한다.

## 6. 파일 배치·품질·비용의 설계

날짜별 파티션에 저장한 데이터에서 특정 날짜 조건을 사용하면 관련 영역만 읽도록 설계할 수 있다. 이를 파티션 가지치기 관점으로 이해하면 저장 용량보다 “쿼리가 얼마나 읽어야 하는가”가 성능·비용에 영향을 주는 이유를 알 수 있다. Athena 문서는 파티션이 스캔 양을 줄일 수 있다고 설명한다.[^d-partition]

Parquet·ORC 같은 열 지향 파일 형식은 필요한 열과 데이터 블록만 읽고 압축을 활용하는 분석에 적합할 수 있다. 그러나 파일을 지나치게 잘게 나누면 목록·열기·작업 스케줄링의 비용이 커지고, 큰 파일로만 합치면 작은 단위 갱신과 병렬성 선택이 달라진다. 데이터 크기·수집 주기·쿼리 조건에 맞는 파일·파티션 배치가 필요하다.[^d-columnar]

분석 결과가 0행이면 수집이 실제로 이루어졌는지와 파티션·조건이 맞는지를 나누고, 열 유형 오류라면 원본 형식·변환·카탈로그 스키마를, 중복이라면 재수집·재시도·중복 제거 기준을 비교한다. 데이터가 늦게 들어오는 문제는 저장소 성능뿐 아니라 원천 이벤트 시각·수집 지연·가공 일정의 차이일 수 있다. Lineage는 이런 원천과 변환 관계를 추적하는 데 쓰이고 품질 검증·권한·보존은 별도의 관리 기능이다.[^v-lineage]
