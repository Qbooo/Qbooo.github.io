## 1. 개요

iSCSI(Internet Small Computer System Interface)는 SCSI 명령과 데이터를 TCP/IP 네트워크를 통해 전달하는 스토리지 프로토콜이다.

서버가 원격 스토리지의 논리 장치에 블록 단위로 접근할 때 사용한다.[^1]

파일 공유 경로를 여는 방식과 달리, 운영체제는 연결된 장치를 디스크와 같은 블록 장치로 다룬다. 파일시스템은 그 위에 구성할 수 있으며, 가상화 플랫폼이나 데이터베이스 등에서 사용하는 방식은 환경에 따라 다르다.

## 2. 주요 구성 요소

| 용어 | 의미 |
|---|---|
| Initiator | SCSI 명령을 보내는 쪽. 일반적으로 서버의 소프트웨어 또는 하드웨어가 담당 |
| Target | 명령을 받아 스토리지 접근을 제공하는 쪽 |
| Logical Unit | SCSI 명령으로 접근하는 논리 장치 |
| LUN | 논리 장치를 식별하는 번호. 운영 현장에서는 제공하는 논리 디스크를 가리키는 표현으로도 사용 |
| Target Portal | Target에 접근할 IP 주소와 TCP 포트의 조합 |
| IQN | iSCSI 노드 이름에 사용하는 형식 중 하나 |

IQN은 이름이고 IP 주소는 접속 위치이다. 서버의 Initiator 이름을 등록하는 것과 네트워크가 연결되는 것은 서로 다른 조건이다.[^1]

## 3. 연결과 데이터 전달

기본적인 흐름은 접속 대상 확인 → 로그인과 매개변수 협상 → 세션 구성 → SCSI 명령 및 데이터 교환이다. 대상 검색은 Discovery 기능이나 관리자가 제공한 설정을 통해 이루어질 수 있다.[^1]

```mermaid
flowchart LR
    A[서버의 Initiator] -->|TCP/IP| B[스토리지의 Target]
    B --> C[논리 장치 · LUN]
```

iSCSI의 기본 TCP 포트는 3260이며, 설정에 따라 다른 포트의 Target Portal을 사용할 수도 있다. 세션과 TCP 연결은 같은 개념이 아니며, 하나의 세션이 여러 연결을 포함할 수도 있다.[^1]

## 4. 파일·오브젝트 접근과의 차이

| 접근 방식 | 클라이언트가 다루는 대상 | 예시 |
|---|---|---|
| iSCSI | 블록 장치 | 원격 볼륨을 연결해 파일시스템 구성 |
| NFS·SMB | 파일과 디렉터리 | 공유 폴더 연결 |
| S3 호환 API | 버킷과 오브젝트 | 오브젝트 업로드·다운로드 |

[[VPSA]]는 iSCSI 등의 블록 접근과 NFS·SMB 파일 접근을 제공한다. [[NGOS]]·[[ZIOS]]는 오브젝트 접근을 제공하므로 iSCSI 디스크 연결 절차와 구분해야 한다.[^2]

## 5. 인증과 다중 경로

CHAP은 iSCSI에서 사용할 수 있는 인증 방식이다. 인증과 데이터 암호화는 별개이므로 CHAP을 설정했다는 이유만으로 통신 내용이 암호화되었다고 볼 수는 없다.[^1]

멀티패스 구성은 여러 경로를 통해 같은 논리 장치에 접근하도록 설정하는 것이다. 실제 경로 장애 처리와 정책은 운영체제·스토리지의 지원 구성에 따른다. VPSA의 서버 정의와 연결 설정도 해당 가이드를 기준으로 확인한다.[^3] 여러 서버에서 같은 장치를 연결했다고 파일 쓰기 충돌이 자동으로 해결되는 것은 아니므로, 동시 접근에 적합한 파일시스템이나 애플리케이션 구성이 필요하다.

하나의 iSCSI 세션에 여러 TCP 연결을 두는 MCS와, 운영체제에서 같은 장치에 대한 여러 I/O 경로를 관리하는 멀티패스는 다른 계층의 개념이다. 세션에 연결이 여러 개 있다는 사실만으로 운영체제의 경로 장애 대응 정책까지 구성된 것은 아니다.[^1]

CHAP은 로그인 시 인증을 위한 수단이다. RFC 7143은 통신 패킷의 기밀성·무결성 보호를 IPsec과 별도로 설명하므로, 인증 설정과 실제 암호화 적용 여부를 분리해 확인해야 한다.[^1]

## 6. 운영체제가 원격 디스크를 인식하는 과정

iSCSI는 파일 이름을 서버로 보내는 프로토콜이 아니라 SCSI 명령을 전송한다. 호스트의 블록 I/O가 SCSI 명령으로 표현되면 Initiator가 이를 iSCSI 메시지에 담아 TCP 연결로 보내고, Target은 해당 논리 장치에 명령을 수행한 뒤 결과와 상태를 반환한다. 실제 데이터가 SSD·디스크 어레이의 어디에 배치되는지는 Target 뒤 저장 계층의 책임이다.[^1] 실물 경로는 호스트 Initiator 소프트웨어·NIC → 스위치와 IP 네트워크 → Target 컨트롤러 → 후단 디스크로 볼 수 있다. IQN은 연결 주체의 이름, IP·포트는 도달할 위치, LUN은 제공할 논리 장치의 식별이라는 서로 다른 질문에 답한다.

연결 전에는 Target Portal의 IP·포트와 Target 이름, 사용할 논리 장치의 매핑이 필요하다. Discovery는 연결 가능한 Target 정보를 찾는 과정이고 Login은 인증·세션 매개변수를 협상하는 과정이다. Login이 성공한 뒤에도 호스트에 제공할 LUN 매핑이 없으면 원하는 블록 장치가 나타나지 않을 수 있다. 따라서 “포트가 열린다”, “로그인된다”, “장치가 보인다”, “파일을 쓸 수 있다”는 서로 다른 단계의 성공이다.[^1][^3]

호스트가 장치를 인식한 뒤에는 일반적인 블록 장치와 마찬가지로 파일시스템이나 애플리케이션을 연결한다. iSCSI 설정에는 NFS의 공유 디렉터리 경로 대신 Initiator·Target·LUN 관계가 핵심이라는 점이 파일 공유와의 큰 차이이다.

## 7. 여러 경로를 사용하는 이유와 한계

멀티패스는 호스트에서 같은 논리 장치에 이르는 여러 경로를 하나의 장치로 관리하는 방식이다. 두 네트워크 포트가 있다고 자동으로 장애 독립성이 생기지는 않는다. 같은 스위치·전원·케이블 구간을 공유하면 그 공통 지점의 장애가 여러 경로에 동시에 영향을 줄 수 있기 때문이다.

경로 정책은 읽기·쓰기 요청을 어느 경로로 보낼지와 장애 시 얼마나 기다렸다가 다른 경로를 사용할지를 결정한다. 스토리지의 컨트롤러 소유권·지원 경로 상태와 운영체제의 멀티패스 정책이 맞아야 한다. RFC의 세션·연결 복구 기능은 프로토콜의 범위이고, 운영체제에서 장치의 경로를 결합하는 구성은 별도의 구현 범위이다.[^1]

또한 멀티패스는 한 서버의 장치 접근 경로를 보호하는 기능이지 두 서버의 파일 쓰기 충돌을 해결하는 기능은 아니다. 경로 이중화, 컨트롤러 이중화, 애플리케이션 이중화는 각각 다른 장애 범위를 다룬다.

## 8. 장애 현상을 통신 단계와 연결하기

TCP 연결이 성립하지 않으면 라우팅·방화벽·주소·수신 포트 같은 전송 경로를 본다. TCP는 연결되지만 Login이 거부되면 Target 이름·Initiator 등록·인증·세션 정책을 확인할 범위가 된다. 장치가 보이지만 읽기·쓰기가 실패하면 LUN 매핑과 접근 권한, 장치 상태와 호스트 I/O 오류를 구별해야 한다. 파일시스템 마운트 실패는 그 위 계층의 문제일 수도 있다.

성능 저하에서는 네트워크 대역폭만이 아니라 왕복 지연과 손실·재전송, 호스트의 I/O 큐, Target의 처리 지연을 함께 해석한다. 작은 동기 I/O는 대역폭이 남아도 매 요청의 지연 때문에 작업이 느릴 수 있다. 반대로 큰 병렬 I/O는 링크 처리량을 먼저 채울 수 있다. 이런 분해는 RFC의 TCP 기반 전송 구조와 블록 I/O 성능 모델을 결합한 해석이다.[^1][^d-io]

CHAP 인증은 접속 주체를 검증하는 한 수단이고 패킷 기밀성을 제공하는 방식은 아니다. 운영망의 접근 경계와 IPsec 등 암호화 조건, 관리·데이터 경로의 보안 요구를 구분해야 한다. 인증 성공만으로 잘못된 LUN 공유 정책이 해결되지는 않는다. LUN masking은 어떤 Initiator에 어떤 논리 장치를 보일지를 정하는 접근 범위이며 CHAP의 신원 확인과 역할이 다르다.

MTU를 크게 하는 구성도 모든 성능 문제의 해결책은 아니다. 경로의 모든 구간이 해당 크기를 일관되게 처리해야 하며, 구성 불일치는 전송 실패·재전송의 원인이 될 수 있다. 지연에 민감한 작은 I/O와 대형 전송의 성능 목표를 먼저 구분하고, 장비·운영체제·서비스가 지원하는 네트워크 구성을 기준으로 판단한다.
