## 1. 개요

Hammerspace(해머스페이스)는 여러 스토리지와 위치에 분산된 비정형 데이터를 하나의 글로벌 네임스페이스로 제공하고, 데이터 배치와 이동을 자동화하는 데이터 플랫폼이다.

기업 이름과 제품 브랜드로 사용한다.[^1]

단순히 디스크 용량을 제공하는 스토리지 장비로만 이해하기보다는, 기존 스토리지의 데이터를 통합해 접근하고 필요한 위치에 배치하는 소프트웨어 플랫폼으로 보는 편이 정확하다.

## 2. 글로벌 네임스페이스

서로 다른 저장 장치·사이트·클라우드의 데이터를 하나의 파일 접근 공간으로 제공하는 개념이다. 사용자는 통합된 경로로 데이터를 찾고, 실제 데이터가 어디에 있는지는 플랫폼이 관리한다.[^1]

경로가 하나로 보인다는 사실과 모든 데이터가 한 장치에 복사되었다는 사실은 다르다. Hammerspace는 기존 위치의 데이터를 통합해 접근하는 기능과, 정책에 따라 데이터를 이동·복제하는 기능을 구분해 설명한다.[^2]

## 3. 데이터 오케스트레이션

데이터 오케스트레이션은 작업에 필요한 데이터를 적절한 위치로 배치하는 관리 기능이다. 여러 스토리지·사이트·클라우드 사이의 데이터 흐름을 정책에 따라 자동화한다.[^2]

*활용 예시: 다른 사이트의 데이터를 GPU 작업 환경 가까이 배치하거나, 처리 후 데이터를 보관용 계층으로 옮기는 구성.*

이는 개념 설명용 예시이다. 지원 프로토콜과 연결 가능한 스토리지, 이동 조건은 제품 버전과 구성에 맞춰 확인해야 한다.

## 4. 기존 스토리지와의 관계

[[Block Storage|블록]], [[File Storage|파일]], [[Object Storage|오브젝트]] 스토리지는 데이터 저장·접근 방식이고, Hammerspace는 여러 저장 자원을 연결해 데이터 접근과 배치를 관리하는 플랫폼이다.[^1]

[[VPSA]]·[[NGOS]]·[[ZIOS]]와 함께 검토할 때는 어떤 인터페이스로 연결하는지와 지원 조건을 확인해야 한다. 이 문서에서 특정 Zadara 제품과의 공식 호환 인증을 확인한 것은 아니다.

소프트웨어 중심이라는 설명이 하드웨어 결합 제품을 판매하지 않는다는 뜻은 아니다. 공식 배포 안내는 범용 서버에 설치하는 소프트웨어, 클라우드 마켓플레이스, 인증된 하드웨어 기반의 통합 어플라이언스 제공 형태를 설명한다.[^1] 연결 가능한 NAS·블록·오브젝트 자원도 실제 버전의 지원 인터페이스와 구성 조건을 기준으로 판단해야 한다.

## 5. 메타데이터와 데이터 경로를 분리한 구성

Hammerspace의 공식 아키텍처는 Anvil 메타데이터 노드와 DSX(Data Services eXtension) 노드를 구분한다. Anvil은 글로벌 네임스페이스·메타데이터와 데이터 이동의 관리 기능을 담당하고, DSX는 클라이언트 프로토콜과 데이터 서비스·이동 작업의 역할을 가진다. 노드는 배포에 따라 물리 서버·VM·클라우드 인스턴스일 수 있다. 기존 NAS·오브젝트·서버의 로컬 저장 공간이 이런 플랫폼에 연결되며, 메타데이터의 위치와 실제 파일 바이트의 위치가 다를 수 있다.[^d-architecture]

클라이언트가 파일 경로를 조회할 때 필요한 메타데이터 처리와 실제 바이트를 읽는 데이터 경로를 구별한다. 지원되는 pNFS 구성에서는 클라이언트가 레이아웃 정보를 사용해 데이터 저장 자원에 직접 접근하는 경로가 가능하고, NFS·SMB·S3 서비스에서는 사용한 프로토콜과 배포 방식에 따른 서비스 경로가 있다. 모든 요청의 파일 바이트가 Anvil을 경유한다고 이해하면 메타데이터 병목과 데이터 전송 병목을 잘못 합치게 된다.[^d-deploy]

기존 데이터의 이름과 접근을 통합하는 Data-in-Place는 모든 파일의 내용을 먼저 다른 디스크로 복사하는 절차와 다르다. 오케스트레이션은 정책에 맞는 위치로 실제 데이터를 배치·이동하는 기능이다. 경로가 같게 유지되는 것과 데이터 위치·복사본이 바뀌는 것을 구별하면 저장 계층을 바꿔도 사용자가 같은 이름으로 접근하는 원리를 이해할 수 있다.

## 6. 데이터 위치가 GPU 처리와 운영에 주는 영향

원격 사이트의 파일을 같은 네임스페이스에서 찾을 수 있어도 WAN을 통해 처음 읽으면 거리·대역폭·원격 저장소 상태의 영향을 받는다. GPU 작업 가까이에 데이터를 미리 배치하는 선택은 실행 중 읽기 지연을 줄일 수 있지만 복사 시간·대상 용량·네트워크 전송과 변경 데이터의 관리가 필요하다. 모든 데이터를 모든 사이트에 두는 방식과 필요한 데이터만 배치하는 방식의 비용도 다르다.[^2]

작은 파일을 많이 조회하는 작업은 메타데이터 처리에, 큰 데이터셋을 읽는 작업은 데이터 경로의 처리량에 민감할 수 있다. 따라서 파일 이름이 보이지만 읽기가 느리다면 메타데이터 응답과 실제 데이터 위치·전송을 분리하고, 대상 저장소가 내려갔다면 이용 가능한 복사본과 정책이 무엇인지 보아야 한다. 정책 이동이 진행되지 않는 경우에는 정책 조건·원본·대상 접근 권한·네트워크·여유 공간·진행 상태를 나누어 해석한다.

성능 판단에서도 글로벌 이름 공간의 편리함과 데이터 locality의 효과를 구분한다. 기존 데이터를 통합해 보이게 한 사실만으로 근접 NVMe에서 읽는 것과 같은 속도가 나오는 것은 아니다. 플랫폼의 역할은 위치·배치·접근을 제어하는 것이고 실제 워크로드에 필요한 대역폭·메타데이터 처리량·보호 조건은 연결한 저장 자원과 배포를 함께 설계해야 한다.
