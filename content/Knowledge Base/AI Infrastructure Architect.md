## 1. 개요

AI 인프라 아키텍트(AI Infrastructure Architect)는 AI 작업에 필요한 컴퓨팅·네트워크·스토리지·운영 소프트웨어를 함께 설계하는 역할이다.

직함과 담당 범위는 조직마다 다르며, 특정 자격증이나 제품 이름을 뜻하지 않는다.

이 문서는 NVIDIA의 AI 인프라 참조 아키텍처를 참고해 학습용으로 정리한 역할 설명이다. 특정 회사의 공식 직무 정의는 아니다. NVIDIA 참조 설계 역시 컴퓨팅·네트워크·스토리지·소프트웨어를 통합된 시스템으로 다룬다.[^1]

## 2. 설계 업무의 구체적인 예

연구팀이 “여러 사람이 같은 GPU 환경에서 모델을 학습하고 싶다”고 요청했다고 하자. 아키텍트는 먼저 모델의 크기, 한 작업에 필요한 GPU 수, 동시에 실행할 작업 수, 데이터셋과 결과의 보관 방식 등을 구체화한다. 막연한 장비 수량 요구를 실제 작업이 실행될 수 있는 구조로 바꾸는 일이다.

한 서버 안에서 끝나는 작업과 여러 노드가 함께 학습하는 작업은 연결 요구가 다르다. 전자는 GPU 메모리와 서버 내부 자원 배치가 중요하고, 후자는 노드 사이 통신과 데이터 공급까지 함께 고려해야 한다. 같은 GPU를 사용해도 서버·네트워크·스토리지의 조합에 따라 작업 완료 시간이 달라질 수 있다.[^1][^d-gpu]

이 과정의 결과물은 장비 목록만이 아니다. 구성도, 자원 규모의 산정 근거, 연결 관계, 선택한 기술의 이유와 검증 결과가 함께 있어야 한다. 실제 장비를 설치하는 엔지니어와 협업하지만, 직무의 중심은 요구사항과 구성 요소 사이의 관계를 설계하는 데 있다. 조직에 따라 설계와 구축을 한 사람이 함께 맡을 수도 있다.

## 3. 설계에서 다루는 영역

| 영역 | 검토할 내용의 예시 |
|---|---|
| 요구사항 | 학습·추론 구분, 데이터 크기, 응답 시간, 예산 |
| 컴퓨팅 | GPU·CPU·메모리, 서버 수와 확장 단위 |
| 네트워크 | GPU 노드 간 통신, 스토리지·관리·외부 연결 |
| 스토리지 | 데이터 읽기 처리량, 용량, 체크포인트 저장·복구 |
| 플랫폼 | 컨테이너·작업 스케줄링, 사용자와 자원 격리 |
| 운영 | 모니터링, 장애 대응, 보안, 변경과 복구 절차 |

네트워크는 노드 간 GPU 통신과 외부·관리 트래픽의 성격이 다르므로 목적에 맞게 구분해 설계한다.[^2]

## 4. 구축 엔지니어와의 관계

역할을 나누는 한 가지 예로, 아키텍트는 요구사항을 구성과 검증 기준으로 구체화하고 구축 엔지니어는 설치·설정·시험을 통해 구현을 확인할 수 있다. 이는 조직마다 다른 업무 분담을 설명하기 위한 예시이며, 보편적인 직무 규정은 아니다.

*산출물 예시: 구성도, 용량 산정 근거, 네트워크 계획, 제품 선택 이유, 성능·장애 테스트 계획.*

GPU 수만 늘리는 것으로 전체 성능이 보장되지는 않는다. 데이터 공급이나 노드 간 통신이 병목이면 GPU를 충분히 활용하지 못할 수 있으므로 전체 흐름을 검증해야 한다.

## 5. 설계 기준과 검증

참조 아키텍처는 직무 명세가 아니라 시스템 설계의 기준이다. NVIDIA 설계는 워크로드·규모·운영 모델·예산에 따라 통합형 또는 전용 네트워크 구성을 선택할 수 있게 한다. 따라서 트래픽의 역할을 구분한다는 설명을 언제나 물리 스위치를 따로 설치해야 한다는 의미로 해석하면 안 된다.[^2]

GPU 연산 성능, 노드 간 통신과 데이터 공급의 균형을 함께 설계하고 실제 워크로드로 검증한다. [[Shell Script]]나 [[SNMP]]는 이러한 운영·관측 체계에 사용할 수 있는 수단이다.

## 6. 업무 요구에 따른 자원·장애 대응 설계

설계의 출발점은 GPU 모델명이 아니라 서비스가 해야 할 일이다. 학습 데이터 크기·모델과 정밀도·학습 또는 추론의 비중·동시 작업·응답 시간·가용성 목표를 자원 요구로 바꾼다. SLO는 사용자에게 제공하려는 품질 목표이고, RPO는 복구 시 허용할 허용 가능한 데이터 손실의 시간 범위, RTO는 복구까지 허용할 시간이라는 서로 다른 요구다. 예를 들어 정기 학습 작업의 완료 시간과 대화형 추론의 응답 지연은 같은 GPU 수량으로 비교할 수 없는 목표다.

데이터 로딩은 스토리지에서 CPU·GPU로, 분산 학습은 GPU 간 집합 통신으로, 체크포인트는 GPU·호스트에서 저장소로 흐른다. 사용자 요청·모델 배포·관리·관측 트래픽도 별도로 존재한다. NVIDIA RA가 east-west·north-south·관리 역할을 구분하는 이유를 이런 데이터 흐름과 연결하면 단순 네트워크 장비 목록보다 설계 근거가 분명해진다.[^2]

논리적인 격리·HA와 물리적인 장애 범위도 연결한다. VM 두 대를 같은 물리 서버나 동일 전원 계통에 두면 호스트·전원 장애에 함께 영향을 받을 수 있다. GPU 서버 수가 늘면 랙 전력·냉각·케이블·스위치 포트와 관리 자원의 요구도 늘어난다. 테넌트의 권한 경계와 물리 전용 장비의 경계는 다르므로 어떤 문제를 어떤 계층에서 해결하는지 설명할 수 있어야 한다.
