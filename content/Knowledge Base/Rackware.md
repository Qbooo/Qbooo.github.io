## 1. 개요

RackWare는 물리 서버·가상 머신·클라우드 환경의 워크로드 이전과 재해 복구를 지원하는 소프트웨어를 제공하는 기업이다.

이 문서에서는 서버 마이그레이션과 DR에 사용하는 RMM(RackWare Management Module)을 중심으로 다룬다.[^1][^2]

RackWare는 회사·브랜드 이름이고 RMM은 제품 구성 요소의 이름이다. 다른 관리 도구에서 사용하는 RMM이라는 약어와는 문맥으로 구분해야 한다.

## 2. 이전과 복구에서 데이터를 동기화하는 이유

서버에는 운영체제뿐 아니라 애플리케이션·설정·업무 데이터가 함께 있다. 장비를 새로 준비하는 것만으로 기존 서비스가 그대로 옮겨지는 것은 아니다. 마이그레이션 도구는 원본 환경의 정보와 데이터를 대상에 준비하고, 그 사이 바뀌는 내용을 반영해 운영 위치를 전환하도록 돕는다.[^1]

예를 들어 원본 데이터 전체를 복사하는 데 오래 걸리면 그동안 새로 생긴 변경분이 남는다. 처음에는 전체 데이터를 옮기고 이후 변경분을 동기화하면 마지막 전환 시 옮길 양을 줄일 수 있다. 다만 애플리케이션 중단·기동과 네트워크 변경 등이 필요할 수 있어 동기화가 곧 무중단을 뜻하지는 않는다.

DR에서는 같은 복제 기술을 사용하더라도 목적이 달라진다. 정상 운영 중에는 복구에 필요한 상태를 유지하고, 장애가 생기면 다른 환경에서 서비스를 이어 가도록 준비한다. 마이그레이션은 운영 위치의 이전, DR은 장애 후 서비스 복구, 백업은 복구 가능한 과거 데이터의 보존이라는 목적의 차이가 있다.[^2]

## 3. 마이그레이션

RMM은 이전 작업을 중앙에서 관리·예약·자동화한다. 공식 Migration 설명은 agentless를 원본·대상에 영구 에이전트 설치가 필요하지 않은 형태로 설명한다. 이는 연결 권한이나 환경별 사전 조건까지 없다는 뜻은 아니다.[^1] 일반적으로 초기 데이터를 대상 환경으로 옮긴 뒤 변경분을 동기화하고, 최종 전환 시점에 마지막 동기화를 수행하는 흐름으로 이해할 수 있다. 실제 단계와 지원 방식은 원본·대상 환경 및 버전에 따라 확인해야 한다.[^1][^3]

- 초기 동기화: 대상 환경에 데이터를 먼저 준비한다.
- 변경분 동기화: 원본에서 새롭게 바뀐 내용을 반영한다.
- Cutover: 원본에서 대상 환경으로 서비스 운영을 전환한다.
- 검증: 대상에서 애플리케이션과 데이터, 네트워크 연결 등을 확인한다.

변경분 동기화는 최종 이전량을 줄이는 데 도움이 되지만, 무중단을 자동으로 보장하지는 않는다. 데이터 변경량과 애플리케이션 종료·시작, 네트워크 전환에 따라 중단 시간이 달라질 수 있다.

## 4. 재해 복구

마이그레이션이 운영 위치를 옮기는 작업이라면, DR(Disaster Recovery)은 장애에 대비해 복구 가능한 환경과 절차를 준비하는 것이다. RackWare는 RMM을 통해 복제와 동기화, 복구 작업을 관리한다.[^2]

- Failover: 장애 등의 상황에서 복구 환경으로 운영을 전환한다.
- Failback: 원래 환경으로 운영을 되돌린다.
- 복구 테스트: 실제 장애 전에 복구 절차와 결과를 검증한다.

도구가 복제를 수행한다고 애플리케이션 복구까지 검증된 것은 아니다. 복구 검증에는 서버 기동뿐 아니라 서비스 응답·데이터 상태·네트워크 연결 확인이 포함된다. Failover·Failback 자동화도 정책과 구성에 따른 기능이며, 모든 환경에서 무설정·무중단 전환을 보장하는 것은 아니다.[^2]

## 5. 이전 작업의 관리 경로와 데이터 경로

RMM은 원본 운영체제·디스크·네트워크와 대상 컴퓨팅 환경 사이의 이전 작업을 관리한다. Agentless라는 설명은 원본·대상에 영구 에이전트를 설치하지 않는 방식이라는 뜻이며, 원격 접속 권한·계정·네트워크·운영체제 지원 조건이 없다는 뜻은 아니다. 제어 서버가 작업을 지시하는 경로와 실제 데이터가 전달되는 경로를 분리해 보면 관리 화면 접속 성공과 데이터 동기화 성공을 구분할 수 있다.[^1]

일반적인 이전 흐름은 원본 정보 파악 → 초기 데이터 복제 → 변경분 동기화 → 마지막 동기화와 전환 → 대상 기동·연결 → 애플리케이션 검증으로 설명할 수 있다. IBM Cloud의 구체적인 예시는 RMM과 네트워크 연결·브리지 서버·대상 서버 준비와 delta sync·cutover를 별도로 구성한다. 이는 해당 환경의 예시이며 다른 대상에서 같은 네트워크 구조가 필수라는 뜻은 아니다.[^3]

대상 OS가 부팅되어도 IP·DNS·인증·외부 DB·라이선스·서비스 시작 조건이 달라 애플리케이션이 실패할 수 있다. 그래서 이미지·디스크 이전과 서비스 운영 전환을 같은 단계로 보지 않는다. 원본·대상이 동시에 쓰기를 받으면 어느 쪽 데이터가 기준인지의 문제가 생기므로 전환 시점과 되돌리기 조건도 설계의 일부다.
