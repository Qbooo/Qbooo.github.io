## 1. 개요

파일 스토리지(File Storage)는 파일과 디렉터리의 계층 구조로 데이터를 관리하고 접근하는 저장 방식이다.

네트워크 파일 스토리지에서는 서버가 제공하는 공유 경로에 클라이언트가 연결해 파일을 읽고 쓴다.[^1]

문서 공유, 사용자 홈 디렉터리, 여러 서버가 사용하는 파일 저장소 등이 대표적인 용도이다.

## 2. 파일 서버와 클라이언트의 역할

예를 들어 회사 공유 폴더에서는 여러 PC가 같은 디렉터리의 문서를 열 수 있다. 각 PC가 원격 디스크의 블록 배치를 직접 해석하는 대신 파일 서버가 파일 이름과 권한, 저장 공간을 관리한다.

네트워크 파일 공유는 클라이언트가 원격 디스크의 블록 위치를 직접 정하는 방식이 아니다. 클라이언트는 경로 조회, 파일 열기, 데이터 읽기·쓰기 등의 요청을 보낸다. 파일 서버는 파일 이름·디렉터리·크기·권한 같은 메타데이터와 실제 저장 공간의 연결을 관리한다. 파일 서버의 저장 기반으로는 로컬 SSD, 디스크 어레이, 블록 스토리지 등을 사용할 수 있다.

파일 하나를 읽는 작업에도 경로 구성 요소의 탐색, 접근 권한 확인, 파일 열기, 데이터 읽기, 닫기 같은 여러 동작이 포함될 수 있다. 따라서 같은 데이터 총량이라도 큰 파일 몇 개와 작은 파일 수백만 개는 부하가 다르다. 작은 파일이 많으면 실제 바이트 전송보다 파일 열기·속성 조회·디렉터리 탐색 같은 메타데이터 동작의 비용이 커질 수 있다. EFS 성능 지침도 파일당 작업 비용과 작은 파일·디렉터리 접근을 따로 다룬다.[^d-perf]

```mermaid
flowchart LR
    A["클라이언트 · 마운트 경로"] -->|"NFS 또는 SMB 요청"| B["파일 서비스 · 권한과 잠금"]
    B --> C["파일시스템 · 메타데이터"]
    C --> D["디스크 또는 스토리지 볼륨"]
```

이 그림은 일반적인 역할의 구분이며 관리형 분산 파일시스템의 내부 구현이 반드시 단일 서버라는 뜻은 아니다.

## 3. 접근 방식

파일 서버는 파일시스템과 메타데이터를 관리하고, 클라이언트는 경로와 파일 이름으로 데이터에 접근한다. 네트워크 파일 공유의 대표적인 프로토콜에는 NFS와 SMB가 있다.[^2][^3]

클라이언트는 공유 경로를 마운트하거나 네트워크 드라이브로 연결한다. 실제 사용 시에는 네트워크 연결뿐 아니라 사용자 인증과 파일·디렉터리 권한도 확인해야 한다.

## 4. 캐시·잠금·동기 쓰기가 필요한 이유

클라이언트 캐시는 자주 읽는 데이터를 재사용하고 작은 쓰기를 묶어 왕복 횟수를 줄인다. 그러나 여러 클라이언트가 같은 파일을 볼 때는 “내가 가진 내용이 언제까지 유효한가”를 프로토콜이 조정해야 한다. 파일 잠금은 특정 범위를 동시에 수정하는 것을 조정하는 수단이며, 서비스가 잠금을 제공하는 것과 모든 애플리케이션이 그 잠금을 올바르게 사용하는 것은 다른 문제이다.[^2]

동기 쓰기는 저장 서비스의 응답을 기다리므로 네트워크 왕복 지연이 애플리케이션의 대기 시간에 직접 드러날 수 있다. 비동기 쓰기는 클라이언트 측 버퍼를 활용해 처리량을 높일 수 있으나, 언제 저장 완료로 간주하는지를 이해해야 한다. EFS 문서도 요청 모델에 따라 지연·처리량·일관성의 특성이 달라진다고 설명한다.[^d-perf]

예를 들어 여러 웹 서버가 이미지를 읽기만 하는 공유와 여러 프로세스가 같은 파일의 내용을 계속 갱신하는 공유는 설계가 다르다. 전자는 읽기 병렬성과 캐시가 중요하고, 후자는 잠금 경합과 갱신 단위, 애플리케이션의 동시성 처리가 중요하다. 파일 스토리지라는 같은 분류 안에서도 작업 특성을 먼저 구분해야 한다.

## 5. 블록 스토리지와의 관계

[[Block Storage|블록 스토리지]]를 제공받은 서버가 그 위에 파일시스템을 만들고 NFS·SMB로 공유하면, 다른 클라이언트에는 파일 스토리지로 보인다. 무엇을 기준으로 분류하는지는 클라이언트에게 제공되는 인터페이스에 달려 있다.

여러 클라이언트가 접근할 수 있어도 같은 파일을 동시에 수정하는 동작이 항상 안전한 것은 아니다. 파일 잠금, 캐시 일관성과 애플리케이션의 동시 접근 방식을 함께 고려해야 한다.

## 6. 제품 예시

| 제품 | 파일 접근 방식 |
|---|---|
| [[VPSA]] | NFS·SMB 파일 공유 |
| Amazon EFS | NFSv4.0·4.1 기반 공유 파일시스템 |
| Amazon FSx for Windows File Server | SMB 기반 Windows 파일 공유 |

위 제품들은 파일을 공유한다는 용도가 비슷하지만 권한 모델, 가용성 구성과 지원 기능이 같지는 않다.[^2][^3][^4]

[[Object Storage|오브젝트 스토리지]]는 일반적인 파일 공유 대신 오브젝트 API로 접근한다. 경로처럼 보이는 이름이 있다고 NFS·SMB 파일시스템과 같은 의미를 갖는 것은 아니다.

파일 접근은 로컬 파일시스템에서도 가능하다. 이 문서의 제품 예시는 그중 네트워크 파일 공유에 초점을 둔다. NFS·SMB는 대표적인 프로토콜이며 파일 스토리지 전체를 이 둘로 한정하는 것은 아니다.

EFS는 파일 잠금과 강한 데이터 일관성을 제공한다. 이런 프로토콜 기능이 있어도 여러 프로그램의 업무상 갱신 충돌까지 자동 해결되는 것은 아니므로 잠금 사용과 동시 수정 정책을 애플리케이션에 맞춰 설계한다.[^2] FSx for Windows는 SMB와 Active Directory 통합을 제공한다.[^3]

S3의 일반적인 키 네임스페이스에서 `images/a.png`의 슬래시는 접두사 구분자로 쓸 수 있지만, 그 자체가 POSIX 디렉터리를 만드는 것은 아니다.[^v-prefix]
