## 1. 개요

Multi-tenancy(멀티테넌시)는 하나의 서비스나 플랫폼이 여러 [[Tenant|테넌트]]를 수용하면서 각 테넌트의 데이터·권한·운영 범위를 분리하는 구조이다.

모든 테넌트가 물리 서버나 데이터베이스 하나를 반드시 공유해야 하는 것은 아니다.[^1]

## 2. 공유와 격리의 모델

| 모델 | 개념 | 고려점 |
|---|---|---|
| Silo | 테넌트별로 자원 묶음을 분리 | 강한 경계를 만들기 쉽지만 자원·운영 비용 증가 가능 |
| Pool | 자원을 공유하고 논리적으로 격리 | 활용률을 높일 수 있지만 정책·애플리케이션 격리가 중요 |
| Bridge(혼합형) | 계층에 따라 전용과 공유 조합 | 요구별 선택이 가능하지만 운영 복잡성 증가 |

물리적으로 분리된 고객 환경도 공통 프로비저닝·운영 체계로 제공될 수 있다. 멀티테넌시는 하드웨어 공유 여부 하나보다 서비스 전체의 관리 모델로 보아야 한다.[^1]

## 3. 격리해야 하는 범위

접근 통제는 API·화면뿐 아니라 네트워크, 저장 데이터, 로그·백업 같은 경로에도 적용되어야 한다. 테넌트 식별자를 요청에 붙이는 것만으로는 충분하지 않으며, 서버가 신뢰할 수 있는 신원과 정책을 기준으로 접근을 검증해야 한다.[^2] 예를 들어 서명된 토큰에서도 발급자·유효성 등을 검증하고 테넌트 컨텍스트를 해석하는 과정이 필요하며, 클라이언트가 임의로 보낸 tenant ID를 그대로 권한 근거로 사용해서는 안 된다.[^1]

성능 측면에서는 한 테넌트의 과도한 사용이 다른 테넌트에 영향을 주는 noisy neighbor 문제가 있다. 할당량, 자원 분배와 측정은 데이터 접근 격리와 별도로 다뤄야 한다. AWS SaaS Lens는 과도한 부하를 유발하는 테넌트를 관측하고 제한하는 전략을 가용성 관리 항목으로 다룬다.[^v-load]

## 4. GPU 서비스에서의 적용

[[GPUaaS]]에서는 GPU·네트워크·스토리지·관리 권한을 함께 나눈다. VM 격리, 전용 할당, 지원 GPU의 분할 기능 등은 구현 수단이며 서비스 전체의 격리를 각각 대신하지는 않는다. [[Zadara Sovereign AI Edge Cloud]]와 같은 플랫폼에서도 실제 제공되는 격리 범위와 관리 책임을 기준으로 해석한다.

## 5. 공유 자원에서 요청 맥락을 유지하는 구조

공유 관리 계층은 여러 테넌트의 가입·계정·배포·계량을 공통 절차로 처리할 수 있다. 실제 애플리케이션 실행 자원은 테넌트마다 전용으로 두거나 일부 계층만 공유할 수 있다. 예를 들어 API와 배포 관리는 공통으로 사용하되 고객별 DB는 전용으로 두는 구성은 혼합 모델의 한 예다. 물리 서버 공유, 애플리케이션 인스턴스 공유, 데이터 테이블 공유는 각각 다른 선택이다.[^1]

요청에 연결된 테넌트 맥락은 API 한 번의 권한 검사로 끝나지 않는다. DB 질의의 데이터 범위, 오브젝트 키나 버킷의 접근 정책, 캐시의 식별 키, 비동기 작업과 로그·백업의 귀속까지 일관되게 이어져야 한다. 클라이언트가 보낸 tenant ID만 믿지 않는 것과 서버 내부에서 그 맥락을 잃어버리지 않는 것이 함께 필요하다.

예를 들어 A의 사용자로 로그인한 뒤 B의 레코드 ID를 요청했을 때 API가 레코드 존재 여부만 보고 반환하면 인증은 성공했어도 격리는 실패한다. 사용자별로 달라야 하는 응답을 캐시하면서 테넌트 맥락을 키에서 빠뜨려도 비슷한 노출이 생길 수 있다. 이는 가능한 설계 오류의 예시이며 특정 제품의 알려진 취약점을 주장하는 것은 아니다. 자원 접근마다 테넌트 범위를 적용해야 한다는 AWS의 설명으로부터 도출되는 원리다.[^d-isolation]

## 6. 성능과 복구에도 테넌트 경계가 필요한 이유

접근이 정확히 분리되어도 한 고객이 CPU·DB 연결·GPU·네트워크를 모두 점유하면 다른 고객의 응답이 느려질 수 있다. quota는 할당 가능한 양, rate limit은 일정 시간의 요청량, 공정 배분은 경합 중 각 작업이 받는 몫을 다룬다. 값이 너무 느슨하면 이웃 간 간섭이 커지고 너무 엄격하면 자원이 남아도 고객 작업을 제한할 수 있다. 공유 효율과 예측 가능한 품질 사이의 설계 선택이다.[^v-load]

고객 A의 부하 뒤 B의 지연이 늘었다면 테넌트별 요청량·실패율·작업 대기·자원 사용량을 같은 시간축으로 비교한다. 플랫폼 전체 평균만으로는 어느 고객이 영향을 받았는지와 어떤 공통 계층이 포화됐는지 알기 어렵다. 테넌트별 계량은 청구뿐 아니라 성능·장애 영향 범위를 설명하는 데도 쓰인다.

백업 복구와 이전에서도 경계가 이어진다. 공유 DB의 전체 백업에서 A만 복원할 수 있는지, 복원 파일·로그가 B에게 노출되지 않는지, 이동 중 예전 위치로 가는 요청이 남지 않는지의 문제가 생긴다. 따라서 격리는 정상 요청의 읽기·쓰기뿐 아니라 운영자의 지원·복구·이전 경로까지 포함하는 시스템 속성이다. 전용 자원이 강한 경계를 만드는 데 유리할 수 있어도 공통 관리 권한과 운영 절차까지 자동 분리해 주지는 않는다.
